The critical research question

How do we know the player just cooked something?

Four separate production pipelines exist, each with its own completion path. The main recipe system — the mixing station — resolves to a single reliable hook.

ScheduleOne.ObjectScripts.MixingStation

Verified in metadata
  1. Player StartButtonClicked() → CanStartMix() Gate: slots filled, output has space.
  2. Client → Host SendMixingOperation()ServerRpc Only the host executes this body.
  3. Host → All SetMixOperation()Observers + Target Populates CurrentMixOperation everywhere.
  4. All clients MixingStart() → fires onMixStart Machine animates; the clock starts.
  5. Tick OnMinPass() / OnTimePass() Decrements CurrentMixTime until IsCurrentMixingOperationComplete().
  6. Host → All ◆ Hook here MixingDone_Networked()ObserversRpc → MixingDone() Reached on every client, after completion is confirmed, while CurrentMixOperation is still populated. Cancelled and partial operations never arrive here.
  7. Host only TryCreateOutputItems()ServerRpc Items appear on clients via slot replication, not locally — never depend on this firing client-side.
  8. All clients OutputChanged() → fires onOutputCollected Optional confirmation that units actually landed.

The Mk2 trap

MixingStationMk2 is a subclass that overrides MixingDone(). A Harmony patch targets one method body, so patching only the base class misses every Mk2 station — and the audited save's own station is mixingstationmk2. Patch both. If the override also calls base.MixingDone(), one batch fires twice, which the idempotency key already absorbs.

Player, save & character identity

Statistics can't leak between characters

The game already keys saves by Steam ID on disk, and exposes the same value at runtime — so identity needs no guesswork.

On disk

Saves\<SteamID64>\SaveGame_N

The save folder is literally named after the owning Steam account.

Per player

Player.json → PlayerCode

The SteamID64 — recorded even for Player_0, the host.

Character name

Game.json → OrganisationName

Chosen at creation. The closest thing to a character identity.

At runtime

LoadManager.ActiveSaveInfo

Carries SavePath, SaveSlotNumber, DateCreated, Networth.

The profile key

SHA256( SteamID64 | OrganisationName | CreationDate | Seed )

Never key on the save slot. Slots get deleted and reused — SaveGame_2 today is not SaveGame_2 next week. CreationDate and Seed are immutable for the life of a save, so the key survives slot churn and cannot collide between two characters.

The field names are reversed from the intuitive reading

In Products.json, the field named Product holds the additive: {Product: "cuke", Mixer: "ogkush", Output: "thickmonkey"} — Cuke is the additive, OG Kush the base strain. Confirm the semantics before building the recipe chain resolver. Getting this backwards would invert every recipe in the cookbook.

Accuracy over counting inventory

Inventory deltas cannot distinguish produced from bought, transferred, or spawned. Every count comes from a completion event instead.

Finding that reshapes the plan

A static recipe table would be wrong

Game.json exposes Settings.UseRandomizedMixMaps — per save. When a player enables it, that save's mixing map is randomized, and any recipe table copied from a wiki is simply incorrect for them.

The planner must read WeedMixMap, MethMixMap, CokeMixMap and ShroomMixMap from the live ProductManager for the currently loaded save, and cache recipe data keyed by profile. This is the strongest argument for building the Game Data Reader properly.

Branch decision · resolved

Build against the Mono branch

Read straight out of Steam's own app metadata for app 3164500 — the alternate branch description:

“Uses Mono instead of IL2CPP as the scripting backend. Less performant than the default version, but less prone to crashes.”

Every class and event in this audit is identical on both branches — only the plumbing changes — so the audit holds either way.

◆ Chosen — alternate (Mono)

Assembly-CSharp.dll is directly patchable, events subscribe with a plain +=, and Harmony behaves normally. Materially less work.

Deferred — default (IL2CPP)

MelonLoader plus Il2CppInterop, generated proxy assemblies, interop delegate wrapping for every event, and marshalling costs that rule out per-frame work. Add once the tracker logic is proven.

Bonus confirmation from the same metadata

Schedule I's Steam Cloud mapping is declared as WinAppDataLocalLow → TVGS/Schedule I/Saves/{64BitSteamID} → *.json. The save tree really is cloud-synced, so keeping our data in %APPDATA%\Schedule1RecipePlanner\ is confirmed rather than assumed.

Phase 9 is where this becomes trustworthy

Cook one batch and get exactly one Production Detected line. Then run the negative tests — each must produce nothing:

  • Start a mix and cancel it
  • Reload a save with a mix already in progress
  • Let an employee finish a batch — logs as employee, not local
  • Move product between storage containers
  • Dry, brick or package existing product
  • Spawn product via the debug console

Identity (Phase 8) lands strictly before detection (Phase 9) — detection without identity writes statistics into the wrong character.
